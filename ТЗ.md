# ТЗ на ITSM-платформу

Nov 5, 2026 · @Gleb Putintsev

Полная спецификация интерфейса: Экраны. Детали для разработки: Реализация.

## 1. Общие сведения

Продукт — коробочная ITSM-платформа для организаций до 5 000 пользователей, с единым кодом для контура заказчика и облака. Рабочее название в ТЗ — «Платформа». Документ задаёт требования к продукту, архитектуру, безопасность, экраны и критерии приёмки.

### 1.1. Цели продукта

Значения ниже — целевые показатели продукта, предложенные в этом ТЗ. Их нужно утвердить до старта разработки.

| Цель | Показатель | Значение |
| --- | --- | --- |
| Быстрый запуск | Время от установки до первой заявки на базовой конфигурации | не более 1 часа |
| Простота для агента | Обучение нового агента до самостоятельной работы | не более 2 часов |
| Простота для пользователя | Создание типовой заявки на портале | не более 60 секунд |
| Настройка без кода | Типовые процессы настраиваются без разработки | не менее 90% сценариев приёмки |
| Безопасность | Открытые критичные и высокие уязвимости на момент релиза | 0 |
| Качество данных | Заявки со связанной услугой или КЕ | не менее 80% через 3 месяца эксплуатации |

### 1.2. Границы продукта

**Входит:** инциденты, запросы и каталог услуг, проблемы, изменения, релизы, база знаний, CMDB, ИТ-активы, SLA, портал, автоматизация, отчёты, ИИ-помощник, API и интеграции.

**Не входит в 1.0:** мониторинг инфраструктуры, RMM и удалённое управление устройствами, полноценный ITOM и AIOps, управление проектами и финансами. Платформа интегрируется с такими системами, но не заменяет их.

### 1.3. Принятые решения

| Вопрос | Решение | Следствие для проекта |
| --- | --- | --- |
| Тип продукта | Коробочный продукт для разных заказчиков | Настройка без форка кода, обновляемость, лицензирование, документация поставки |
| Регулирование | Российские и международные требования | Общее ядро контролей и профили RU и INT |
| Развёртывание | Контур заказчика и облако | Единый код, закрытый контур без интернета, мультиарендность в облаке |
| Масштаб первой версии | До 5 000 пользователей | Модульный монолит вместо микросервисов |

### 1.4. Допущения, требующие подтверждения

- До 500 агентов и до 300 одновременных сессий на одну инсталляцию.
- До 2 000 новых заявок в сутки, пиково 100 в минуту при массовом сбое.
- До 200 000 КЕ в CMDB и 5 лет хранения заявок.
- Интерфейс на русском и английском, локализация расширяется без изменения кода.
- Команда владеет Java, Go, Python, Kubernetes и React либо готова их освоить.

### 1.5. Термины

| Термин | Значение |
| --- | --- |
| Заявка | Общая запись обращения: инцидент, запрос, проблема или изменение |
| Инцидент | Незапланированное прерывание или снижение качества услуги |
| Запрос | Обращение на стандартное действие из каталога |
| Проблема | Причина одного или нескольких инцидентов |

| Агент | Сотрудник, обрабатывающий заявки |
| Арендатор | Изолированная организация в облачной инсталляции |
| Инсталляция | Один развёрнутый экземпляр Платформы |

Каждое требование имеет идентификатор, например `INC-03`, и целевой релиз: **MVP**, **1.0** или **2.0**. Содержимое и последовательность релизов описаны в разделе 13.

## 2. Что взять у лидеров рынка

Платформа сочетает простоту Freshservice, глубину модели данных ServiceNow, связку с разработкой Jira и развёртывание у заказчика, как у российских систем. Внутренняя архитектура закрытых продуктов не опубликована, поэтому сравнение опирается на публичные материалы, отзывы и функции.

| Система | Что взять | Чего избежать |
| --- | --- | --- |
| [ServiceNow](https://www.g2.com/categories/it-service-management-tools) | Сервисная модель CMDB по образцу [CSDM](https://www.servicenow.com:443/community/s/cgfwn76974/attachments/cgfwn76974/common-service-data-model-kb/243/1/CSDM%204.0%20Draft%20V2.pdf), влияние КЕ на услуги, развитые изменения | Высокий порог входа, цена и сложность, на которые жалуются пользователи G2 |
| [Freshservice](https://www.trustradius.com/compare-products/freshservice-vs-servicenow-it-service-management) | Готовность из коробки, простой интерфейс агента и пользователя, ИИ в базовом сценарии | Меньшая глубина CMDB и изменений по оценкам TrustRadius |
| [Jira Service Management](https://www.siit.io/tools/comparison/freshservice-vs-jira-service-management) | Связь с разработкой и DevOps, автоматические изменения из CI/CD | Зависимость от большой настройки и функций, закрытых старшими тарифами |
| [ManageEngine ServiceDesk Plus](https://www.manageengine.com/products/service-desk/itsm/itsm-gartner-magic-quadrant.md) | Сертификация практик ITIL, встроенный ИИ без доплаты, развёртывание у заказчика | Перегруженность функциями и формами (гипотеза, проверить на пользователях) |
| [NinjaOne](https://g2.com/categories/it-service-management-itsm-tools/small-business) | Простота как главное конкурентное преимущество | Смещение в управление устройствами, вне границ продукта |
| [InvGate](https://www.ninjaone.com/blog/best-itsm-tools/) | No-code, визуальная CMDB, единый вид ITSM и активов | Слабые места не изучены, проверить на демо |
| [iTop](https://wikidocs.net/blog/@easyeng/8872/) | Расширяемая объектная модель CMDB, связи как отдельные сущности | Слабое автообнаружение, ограниченная автоматизация |
| [SimpleOne](https://toolfox.ru/services/s/intraservice/alternatives) | Low-code, сертификация ITIL 4, отечественная инфраструктура | Закрытые цены, которые затрудняют оценку |
| [Okdesk](https://a2is.ru/catalog/service-desk/simpleone-itsm/alternatives-simpleone-itsm) | Понятный интерфейс и интеграция с Active Directory | Многие модули оплачиваются отдельно |

**Как Платформа отличается от лидеров:**

1. Базовая конфигурация работает сразу и настраивается мастером, без внедренческого проекта.
2. Безопасность с профилем для закрытого контура встроена в ядро, а не продаётся отдельным тарифом.
3. ИИ работает на локальной модели заказчика, внешние модели по умолчанию отключены.
4. Все ключевые функции входят в одну редакцию, а тарифы различаются масштабом и поддержкой.

**Методология.** Основа процессов — практики ITIL. [ITIL 5 вышла в феврале 2026 года и сохранила все 34 практики ITIL 4](https://www.apwide.com/?p=8231), поэтому привязка к конкретным практикам устареет не скоро. Перед [сертификацией процессов](https://www.manageengine.com/products/service-desk/itsm/itsm-gartner-magic-quadrant.md) нужно сверить продукт с действующей схемой PinkVERIFY.

## 3. Роли и права доступа

Доступ запрещён по умолчанию и складывается из роли (RBAC) и атрибутов записи (ABAC). Роль определяет допустимое действие, а атрибуты — конкретные записи, к которым оно применимо.

### 3.1. Роли

| Код | Роль | Назначение |
| --- | --- | --- |
| REQ | Заявитель | Создаёт обращения и видит свои заявки и заявки своей области |
| APR | Согласующий | Согласует запросы и изменения, назначенные ему |
| AGT | Агент | Обрабатывает заявки своих групп |
| LEAD | Руководитель группы | Распределяет работу, видит показатели группы, переопределяет назначения |
| MIM | Менеджер крупных инцидентов | Объявляет и ведёт крупные инциденты |
| CHG | Менеджер изменений | Ведёт изменения, календарь и CAB |
| PRB | Менеджер проблем | Ведёт проблемы и известные ошибки |
| KNW | Редактор знаний | Создаёт, проверяет и публикует статьи |
| CFG | Менеджер конфигураций | Управляет CMDB и правилами сверки |
| AST | Менеджер активов | Управляет активами, лицензиями и договорами |
| ANL | Аналитик | Читает отчёты и строит дашборды |
| ADM | Администратор платформы | Настраивает формы, процессы, каталог, SLA и интеграции |
| SEC | Администратор безопасности | Управляет ролями, политиками, ключами и журналами |
| AUD | Аудитор | Только чтение записей и журналов в рамках области аудита |
| SVC | Сервисная учётная запись | Выполняет интеграции с минимальными областями API |
| AI | ИИ-агент | Действует от имени пользователя и в пределах его прав |

## 5. Жизненные циклы и бизнес-правила

Статусы, приоритеты и сроки ниже — значения по умолчанию, которые администратор может изменить без разработки. Любой переход проверяет права и обязательные поля и записывается в журнал.

### 5.1. Инцидент

&#91;embedded content: жизненный цикл инцидента · 7 статусов\]

Пауза SLA действует только в статусе «Ожидание» и только с указанной причиной. Возврат из «Решена» возможен до автозакрытия, после него создаётся новая связанная заявка.

| Переход | Кто | Обязательные условия | Системное действие |
| --- | --- | --- | --- |
| Новая → Назначена | AGT, LEAD, правило | Группа | Запуск OLA, уведомление группы |
| Назначена → В работе | AGT | Исполнитель | Фиксация времени реакции |
| В работе → Ожидание | AGT | Причина, срок возврата | Пауза SLA, напоминание |
| Ожидание → В работе | AGT, ответ заявителя, таймер | Нет | Возобновление SLA |
| В работе → Решена | AGT | Код и описание решения | Фиксация времени решения, письмо заявителю |
| Решена → В работе | Заявитель, AGT | Комментарий, если заявка не закрыта | Счётчик возвратов +1 |
| Решена → Закрыта | Таймер, заявитель, LEAD | Срок ожидания истёк | Опрос удовлетворённости |
| Новая → Отменена | Заявитель, AGT, LEAD | Причина | Уведомление участников |

### 5.2. Приоритет

Приоритет определяется влиянием и срочностью. Ручное изменение требует причины и видно в журнале.

| Влияние / срочность | Высокая | Средняя | Низкая |
| --- | --- | --- | --- |
| Высокое (услуга или организация) | P1 | P2 | P3 |
| Среднее (подразделение) | P2 | P3 | P4 |
| Низкое (один пользователь) | P3 | P4 | P4 |

### 5.3. Сроки SLA по умолчанию

| Приоритет | Реакция | Решение | График |
| --- | --- | --- | --- |
| P1 | 15 мин | 4 часа | 24×7 |
| P2 | 30 мин | 8 часов | 24×7 |
| P3 | 4 часа | 2 рабочих дня | Рабочий график |
| P4 | 8 часов | 5 рабочих дней | Рабочий график |

### 5.4. Запрос

Статусы: Черновик → Новая → На согласовании → Согласована → В работе → Выполнена → Закрыта. Из «На согласовании» возможен переход в «Отклонена», из любого активного статуса до выполнения — в «Отменена». Отклонение требует причины и уведомляет заявителя.

### 5.5. Проблема

Статусы: Новая → Анализ → Причина установлена → Известная ошибка → Устранение → Решена → Закрыта. Закрытие требует заключения о причине и результата проверки либо решения принять риск с указанием владельца и срока пересмотра.

### 5.6. Изменение

| Статус | Вход | Кто переводит | Что проверяется |
| --- | --- | --- | --- |
| Черновик | Создание | Автор | Нет |
| Оценка | Отправка | Автор | Планы внедрения, проверки и возврата, КЕ, окно |
| Согласование | Оценка риска завершена | CHG | Маршрут согласования, конфликты, заморозка |
| Запланировано | Все согласования получены | Система | Автор не среди утверждающих |
| Внедрение | Наступление окна | Исполнитель | Текущее время внутри окна |
| Проверка | Шаги выполнены | Исполнитель | Результат каждого шага |
| Разбор | Проверка завершена | CHG | Результат: успешно, частично, откат |
| Закрыто | Разбор завершён | CHG | Заключение, связанные инциденты |

Стандартное изменение из шаблона пропускает «Оценку» и «Согласование». Экстренное идёт по сокращённому маршруту, а последующее согласование обязательно в течение 2 рабочих дней. Статусы «Отклонено» и «Отменено» доступны до начала внедрения.

### 5.7. Статья знаний

Статусы: Черновик → На проверке → Опубликована → На пересмотре → Архив. Автор не может утвердить свою статью, если включена проверка четырёх глаз. Срок пересмотра по умолчанию — 12 месяцев.

### 5.8. Правила распределения

1. Прямое назначение из правила или предложения каталога.
2. Группа, ответственная за услугу или КЕ.
3. Подсказка ИИ, только если уверенность выше порога и режим включён.
4. Внутри группы: по кругу или по наименьшей загрузке с учётом графика и навыков.
5. Группа по умолчанию, если ни одно правило не сработало.

## 6. Архитектура

Платформа строится как модульный монолит на Java с отдельным фоновым обработчиком и изолированным ИИ-шлюзом. Для 5 000 пользователей и установки в контур заказчика микросервисы дадут больше эксплуатационных рисков, чем пользы.

&#91;embedded content: логическая архитектура · 5 слоёв\]

Запросы идут сверху вниз. Ни один клиент не обращается напрямую к данным, секретам или ИИ-модели.

### 6.1. Ключевые архитектурные решения

| ID | Решение | Почему | Что отвергнуто |
| --- | --- | --- | --- |
| ADR-01 | Модульный монолит с жёсткими границами модулей | Простая поставка и обновление, транзакции без распределённых компенсаций | Микросервисы: много компонентов и версий на каждой площадке |
| ADR-02 | Модули общаются через публичные интерфейсы и доменные события, проверка границ в CI | Модуль можно выделить в сервис без переписывания | Прямой доступ к таблицам чужого модуля |
| ADR-03 | Transactional outbox в PostgreSQL | Гарантия доставки без отдельного брокера | Обязательный Kafka: тяжёл для минимальной установки |
| ADR-04 | Kafka только как опциональный коннектор экспорта событий | Удобно для заказчиков, у которых он уже есть | Kafka в ядре |
| ADR-05 | Метаданные настраиваемых полей в таблицах, значения в JSONB с индексами | Настройка без миграций и без entity-attribute-value | Динамические `ALTER TABLE` для каждого поля |
| ADR-06 | Конфигурация хранит версии и переносится между средами | Обновление продукта не ломает настройки | Правки конфигурации только на продуктиве |
| ADR-07 | Мультиарендность через `tenant_id` и RLS, отдельная БД как опция | Баланс цены и изоляции, on-prem работает как один арендатор | Отдельный форк продукта под облако |
| ADR-08 | Отдельные региональные облачные контуры RU и INT без репликации между ними | Простое выполнение требований к локализации и юрисдикции | Единый глобальный контур |
| ADR-09 | ИИ вынесен в отдельный сервис и сетевой сегмент | Сбой или взлом ИИ не затрагивает ядро, учтён проект требований ФСТЭК | ИИ-библиотеки в основном процессе |
| ADR-10 | Вложения в S3 через подписанные ссылки после проверки | Ядро не отдаёт файлы напрямую, снижается нагрузка и риск | Хранение файлов в БД |

### 6.4. Ключевые потоки

**Обращение из почты:**

1. Обработчик забирает письмо и проверяет SPF, DKIM и DMARC.
2. HTML очищается, файлы уходят на проверку, вредоносные получают карантин.
3. Определяется отправитель, а токен в письме связывает ответ с заявкой.
4. Модуль tickets создаёт запись и событие в одной транзакции.
5. Outbox передаёт событие в SLA, автоматизацию, индексацию и уведомления.
6. Клиенты получают обновление очереди через WebSocket.

**Запрос к ИИ:**

1. API-сервис проверяет права и извлекает только записи, разрешённые пользователю.
2. Шлюз маскирует секреты и персональные данные согласно политике.
3. Содержимое заявок передаётся как данные, а не инструкции, и проходит фильтр.
4. Модель отвечает, шлюз проверяет ответ и фиксирует запрос в журнале.
5. Предлагаемые действия выполняет API-сервис с проверкой прав и нужным подтверждением.

## 7. Модель данных

Общая таблица `ticket` хранит единые поля всех типов заявок, а специфичные данные лежат в связанных таблицах. Каждая запись содержит `tenant_id`, UUIDv7 в качестве первичного ключа и служебные поля аудита.

### 7.1. Общие правила

- Служебные поля любой таблицы: `id`, `tenant_id`, `created_at`, `created_by`, `updated_at`, `updated_by`, `version`.
- Время хранится в UTC в типе `timestamptz`, а часовой пояс применяется при показе.
- Оптимистичная блокировка выполняется по `version`, конфликт возвращает HTTP 409.
- RLS включена на всех таблицах с `tenant_id`, приложение работает под ролью без `BYPASSRLS`.
- Миграции обратно совместимы в пределах двух соседних версий.
- Физическое удаление выполняется только процессом хранения и удаления данных.

### 8.3. Вебхуки и события

Вебхук подписывается HMAC-SHA256 и содержит идентификатор события, время и версию схемы. При ошибке доставка повторяется с экспоненциальной задержкой 8 раз, затем событие попадает в очередь неудачных с возможностью повтора вручную. Получатель обязан обрабатывать повторы идемпотентно.

```json
{
  "id": "01J9Z8X7N5V3K2",
  "type": "ticket.status_changed",
  "schema_version": 1,
  "occurred_at": "2026-11-05T10:15:00Z",
  "tenant": "acme",
  "data": {"ticket_id": "...", "from": "in_progress", "to": "resolved"}
}
```

### 8.5. Безопасность интеграций

- Исходящие запросы идут через единый модуль, адреса внутренних сетей и служб метаданных запрещены.

## 10. Интерфейс

Платформа состоит из четырёх пространств: портал, рабочее место агента, управление и вход. Элемент появляется только при наличии права, но проверка прав всё равно выполняется на сервере.

Этот раздел задаёт общую структуру. Источник истины для реализации — вкладка Экраны, и при расхождении действует она.

| NFR-13 | Отказоустойчивость | Отказ узла не прерывает работу, недоступность поиска, кэша или ИИ снижает функции, но не блокирует заявки | Хаос-тесты |
| NFR-14 | Обновление | Без простоя внутри основной версии, в остальных случаях окно до 30 минут и документированный откат | Тест обновления |
| NFR-15 | Совместимость клиента | Две последние версии Chrome, Edge, Firefox, Safari, Яндекс Браузера | Автотесты |
| NFR-16 | Покрытие | Доменная логика не менее 80%, все правила доступа покрыты тестами | CI |
| NFR-17 | Поддерживаемость | Границы модулей проверяются автоматически, ADR для существенных решений | CI, ревью |
| NFR-18 | Срок поддержки | Выпуск LTS поддерживается 24 месяца, обновления безопасности не прекращаются в течение этого срока | Документ политики |

## 12. Развёртывание и эксплуатация

Единый подписанный Helm-чарт устанавливает Платформу в любой Kubernetes, в том числе без доступа к интернету. Для пилота предусмотрена одноузловая конфигурация, а для промышленной работы — трёхузловая HA.

### 12.1. Конфигурации

Ресурсы ниже — предварительная оценка, которую уточняют нагрузочные тесты. Объём зависит от вложений и включённого поиска.

| Параметр | Пилот | Промышленная HA, до 5 000 пользователей |
| --- | --- | --- |
| Узлы приложения | 1 узел, 8 vCPU, 32 ГБ | 3 узла, по 8 vCPU, 32 ГБ |
| PostgreSQL | На том же узле | Primary и 2 реплики, по 8 vCPU, 32 ГБ, SSD 1 ТБ |
| OpenSearch | Заменён поиском PostgreSQL | 3 узла, по 4 vCPU, 16 ГБ, SSD 500 ГБ |
| Хранилище S3 | 200 ГБ | От 2 ТБ, с репликацией |
| ИИ-модель | Отключена | Отдельный GPU-узел по выбору модели |
| Назначение | Пробная эксплуатация, не для ПДн | Продуктивная среда |

### 12.2. Состав поставки

- Подписанные образы контейнеров и Helm-чарты, а также SBOM и контрольные суммы.
- Офлайн-комплект: образы, зависимости, модель языкового анализа, установщик.
- Спецификация API и образцы коннекторов.
- Руководства: администратора, пользователя, агента, безопасности, по восстановлению.
- Для профиля RU: материалы для модели угроз, описание мер, формуляр и другие документы по требованию заказчика.
- Лицензионный файл с подписью, без обращения к серверу вендора.

### 12.3. Установка и обновление

1. Предварительная проверка: версия Kubernetes, ресурсы, хранилище, сеть, DNS, сертификаты.
2. Проверка подписи всех артефактов.
3. Резервное копирование и проверка совместимости перед обновлением.
4. Применение обратно совместимых миграций и поочерёдное обновление компонентов.
5. Автотесты работоспособности после обновления.
6. Завершающая стадия миграций после проверки стабильности, откат образа до этого момента.

Обновление проходит не более чем через одну основную версию. Настройки заказчика хранятся как данные, поэтому не ломают обновление.

### 12.4. Резервное копирование и восстановление

- PITR для PostgreSQL с копией WAL каждые 5 минут и полной копией раз в сутки.
- S3-версионирование и копия в отдельный бакет или площадку.
- Индекс OpenSearch воссоздаётся из БД, копия нужна только для ускорения.
- Ключи шифрования копируются отдельно от данных.
- Учения по восстановлению проводятся не реже раза в квартал, в поставке есть сценарий проверки.

### 12.5. Наблюдаемость

| Сигнал | Что собирается | Оповещение по умолчанию |
| --- | --- | --- |
| Доступность | Состояния компонентов и синтетический сценарий создания заявки | Сбой сценария в течение 5 минут |
| API | Частота, ошибки, задержки по эндпоинтам | Ошибки 5xx выше 1% за 5 минут, p95 выше цели |
| Очереди | Глубина outbox, возраст события, неудачные доставки | Возраст старше 5 минут |
| SLA-движок | Отставание расчёта таймеров | Больше 60 секунд |
| Почта | Отставание и ошибки каналов | Отставание больше 5 минут |
| БД | Подключения, блокировки, репликация, долгие запросы | Отставание реплики больше 30 секунд |
| Копии | Статус и возраст копии, результат проверки | Копия старше 26 часов |
| Безопасность | Раздел 9.3, SEC-33 | Немедленная отправка в SIEM |

Логи пишутся в JSON с `trace_id` и не содержат паролей, токенов и текста заявок. Экран «Обслуживание» показывает сводку и выгружает диагностический пакет с очисткой чувствительных данных.

### 12.6. Поддержка продукта

На старте действуют уровни поддержки P1–P4, каналы обращения и порядок обновлений для закрытых контуров. Поддержка получает доступ к данным заказчика только через временное, подтверждённое заказчиком и записанное в журнал разрешение.

- [ ] Готовы документация, SBOM, подписи, заметки к релизу и руководство по безопасной настройке.
